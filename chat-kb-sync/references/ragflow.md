# 本地 RAGFlow：部署、入库、检索与恢复

本流程面向 RAGFlow **1.0.0 的 Go API** 和专门的私有聊天资料集，不自动修改已有文档库、聊天助理、Docker 项目、卷或模型配置。未把其它版本列为通过兼容性验证。下文先用合成资料演练，再处理获准资料。

## 1. 从未安装到网页可用

1. 先问清部署目录、平台、内存／磁盘余量、可用端口，以及是否有现成 RAGFlow。复用已有实例前确认版本与权限，不重装覆盖。新装按 [RAGFlow 1.0.0 官方 Docker Quickstart](https://ragflow.io/docs/v1.0.0/) 固定发行标签和镜像，不用可漂移的 nightly。官方起点是 4 核、16 GB 内存、50 GB 磁盘及 Docker 24／Compose 2.26.1 以上；Windows 用支持 Linux 容器的 Docker Desktop。检查 Docker 宿主（Windows 上通常是 Linux VM）的 Elasticsearch `vm.max_map_count`。
2. 在新 RAGFlow checkout 中核对 `docker/.env`、端口和密钥，确认 Docker Compose 最终设置。限制**所有**容器依赖和应用的主机发布端口：不必对主机公开的端口取消发布；必须访问的端口绑定 `127.0.0.1`（使用当前 Docker Compose 已验证支持的覆盖语法），不把默认数据库凭据、MinIO、管理或 API 端口暴露给局域网或公网。先查看 `docker compose config` 的实际绑定；输出可能含有密码，不上传、不要放进会话。需要本机示例网页端口时可选 8081（须先检查没有占用）。
3. 有启动授权后，在上游 checkout 的 Docker 目录运行官方 Compose 命令，检查容器状态及同一个网页端口的 `/api/v1/system/healthz`；健康就绪后再登录网页。不要以容器进程存在代替健康检查。排错和升级参照 [官方 FAQ](https://ragflow.io/docs/v1.0.0/faq)；不要运行会移除卷的命令。
4. 从 RAGFlow 用户设置取本地 **RAGFlow API Key**（并非 LLM 的 key），由当前用户的私有密钥存储、进程环境或只给任务用户读的私有启动文件注入 `RAGFLOW_API_KEY`。不要粘在提示词、命令参数、仓库配置或日志中。

如果还要导入项目 PDF、扫描件、图片或 Word，另建项目资料集，不与聊天归档混放。先用一份可搜索 PDF、一份扫描件、一张含文字图片验证正文、表格与页码来源；保留原始目录、名称和来源标记，按地点或项目隔离。RAGFlow 1.0 的本地 DeepDoc OCR 与外部模型看图是两条不同路线；后者单独批准。无文字 OCR 结果要记为不可检索，不把上传成功算成检索成功。文档允许哪种模型处理、原文能否外发，应在实际导入和云端问答前分别确认。

## 2. 准备专用聊天资料集

只在用户批准创建新资料集之后运行以下命令；按实际端口替换示例，不修改现有资料集：

```text
python chat-kb-sync/scripts/ragflow_local.py --origin http://127.0.0.1:8081 create-dataset ChatKB-Personal --language Chinese
```

保存返回的资料集 ID，在网页核实名称和私有权限。创建命令遇到同名资料集直接停止，不认领它。如 API 请求返回不确定，先在网页核对是否已创建，不能盲目换名反复提交。

只支持 `ChatKB-` 前缀的私有空库首次绑定，使用 General 内置解析、全文索引，没有向量模型、VLM 或启用的自动提取。不把资料集绑定到云模型问答、自动编译、知识图谱或团队共享。常规 RAGFlow 向量问答的 LLM 设置并不是本地全文入库的前提；如要问答，先单独确认会不会将提问和命中的资料发给外部模型。

脚本只接受明确的 `http://127.0.0.1[:port]` 或 `http://[::1][:port]`，不用代理，不跟随重定向。宿主机、该端口的运行者以及 RAGFlow 的内部网络仍要可信：脚本不能替容器防火墙保证没有外发。如果发布版本或服务器回读的模型设置不符，保留原资料集、用专用测试实例排查，不关闭核对逻辑。

## 3. 验收与运行

- 归档主程序先在批准的私有工作目录生成候选总结；确认该路径不是版本库、云同步盘或共享文件夹。该目录中的 `outbox/<64 位十六进制 topic_id>.md` 是待发布内容，不得将未经审批的草稿和原始聊天混入。归档主程序走显式 topic ID 白名单；直接使用以下发布命令则把 **受控 outbox 的所有匹配文件** 当作已批准资料：

```text
python chat-kb-sync/scripts/ragflow_local.py --origin http://127.0.0.1:8081 publish "<PRIVATE_WORK_DIR>" "<DATASET_ID>"
```

- 第一遍可能只上传和排队解析。出口状态 `2` 代表还有待完成或失败项，不代表已经入库，可隔一段时间重跑同一条命令。每次最多尝试推进 40 篇有变化的文档；保持任务单实例，不要同时在网页更改正在管理的文档。
- 逐篇验证上传文件内容、解析状态和只限该文档的全文检索。验收先发一篇合成主题、更新同主题同 ID、再写第二个主题；核对旧正文不再作为启用版本检索，新版和新主题各可检索，重复运行无新上传。用户真正关心的关键字和原文来源另外抽查，不仅查脚本的版本标记。
- 文件以 TXT 纯文本导入（原本地 Markdown 不变），不加载链接和附件。RAGFlow 的文件名包含稳定话题 ID 与内容摘要哈希；标题与来源在文件内容中。第一次启动后保存 `ragflow-state.json`，它是不含正文和令牌的私有事务记录，但含有索引 ID，别放进公开仓库。跨日漏跑无需改写源文件时间。
- `unchanged` 表示内容与上次成功提交的版本相同，不是每晚重查所有已索引文档。如果有人在网页更改／删除资料，请先核实远端与本地状态，不要重建状态来强制认领已有资料集。

## 4. 更新边界与恢复

RAGFlow 的文档配置接口不直接原地替换已上传的文件内容。默认 `revision` 选择**新版本上传 → 解析 → 全文读回 → 停用旧版 → 提交状态**。未切换时旧版本保留可搜索；切换故障处可能短时出现两版，不能宣称原子切换或严格一次投递。脚本以内容哈希和明确 ID 尽力恢复；异常时保留双方副本而不是删除。停用不会清理历史版本。

出现失败时，先用专用库界面检查解析状态、旧版可用性和正常权限；网络或服务恢复后用同一工作目录、实例和资料集重跑。若需人工切回旧版，由用户明确选择该主题的旧文档，先核实它可搜索再停用故障新版，同时保留状态和两份材料，暂停定时任务，处理状态与页面不一致后再继续。意外导入敏感材料应另行启动用户批准的隔离与删除流程；删除源文件不意味着远端被删除。

## 5. 同题原位更新检索（可选）

- 新建私有空库和独立工作目录，在首次发布前设 `ragflow.update_mode: "inplace-index"`。同话题使用同一个 RAGFlow 文档 ID，不重复上传；换话题仍按新主题标识新建。已有 `revision` 台账不允许直接切换，也不自动迁移、合并或删除旧文档。
- 本地 Markdown 是最新正文。此模式通过 [更新检索分块](https://ragflow.io/docs/v1.0.0/http_api_reference#update-chunk) 更新同一文档的已存在分块；验证正文和检索后，停用多余的旧分块。**不替换可下载的上传原件。不要在 RAGFlow 网页重新解析管控中的文档**，重解析会从初次上传的文件恢复旧内容。需要 RAGFlow 下载原件总是最新版时，保留默认 `revision`。
- 仅适用于这套工具创建的 General 全文 TXT 私有归档，不用于 PDF、图片或启用向量／自动提取的库。正文加版本标记限制 24 KiB 和 9,500 个字符，无可编辑分块或超限则失败并保留本机笔记；不截断，也不回退到新增版本或调用模型。
- 验收从仓库目录运行 `python tests/live_ragflow_acceptance.py --origin http://127.0.0.1:8081 --execute`（用你实际的本机端口和已私下设置的 RAGFlow API Key）。它只创建、使用并清理一个随机命名的虚构资料集：同题改长及改短、验证中文和拉丁字母检索、检查没有旧文本或新增文档、换题新增一份以及重复不增。不要在正式库里手动验证删除或重新解析。

## 接口依据

[RAGFlow 1.0 HTTP API](https://ragflow.io/docs/v1.0.0/http_api_reference) 的资料集管理、上传／查询／更新文件、内置解析、按文档检索；[官方文档的引用检索概念](https://ragflow.io/docs/v1.0.0/chunk_parsing_results_and_knowledge_fragment_management)。启用外部模型是独立审批；只读 MCP 查询如有需要也应独立授权，限特定资料集及文档，不暴露全账号能力。
